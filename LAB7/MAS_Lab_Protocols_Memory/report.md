# Бюро бронирования: протоколы и память

Полный запуск: **6/6**.

| Сценарий и предмет решения | Правило, альтернатива и контрпример |
|---|---|
| **1. Уточнение.** | Условия текущей заявки дополняются сохранёнными полями, а явно переданные новые значения имеют приоритет; уточнение продолжает ту же A2A Task, тогда как `search_rooms` вызывается агентом как MCP-операция. Альтернатива — строить требования только из очередной реплики. Тогда сообщение `{time: "10:00"}` после заявки с датой и числом участников потеряет обязательные поля и вместо предложения вызовет новое уточнение. |
| **2. Перезапуск.** | В checkpoint сохраняются владелец, task/context ID, требования, фаза, предложение и результат бронирования; A2A Task наблюдается отдельно, но не заменяет прикладной снимок. Альтернатива — сохранить только требования. После перезапуска подтверждение не знает предложенную `A-101` и не может корректно подтвердить именно её. **Трасса:** taskId `bfa6933e-aba8-4abf-a003-476fe79d0042`; строки 13 (`agent.restart`) и 17 (`mcp.tool.call`). |
| **3. Новый диалог.** | Профиль меняется только отдельной валидной инструкцией `remember`; запись содержит корпус, ID сообщения-источника и номер ревизии. Новый Task читает этот профиль как долговременную память, а не восстанавливает старую переписку. Альтернатива — запоминать корпус из любой заявки. Тогда разовый выбор B для одной встречи станет скрытой установкой профиля и исказит следующую независимую заявку. |
| **4. Разовое исключение.** | Явный корпус в текущем `patch` важнее сохранённого предпочтения: память заполняет лишь отсутствующий корпус; без `remember` профиль не переписывается. Альтернатива — всегда накладывать профиль после заявки. При памяти B и явной просьбе A агент предложит B, хотя пользователь запросил A; обратная запись A в память также испортит следующие заявки, хотя следующая независимая задача вправе снова использовать B. |
| **5. Перемешанные обращения.** | Снимок адресуется однозначной парой `(user_id, task_id)`, закодированной без коллизий; `contextId` не является ключом задачи. Альтернатива — ключ только по пользователю или контексту. У Alice две Task в одном `shared-conversation`: заявка на A 6 ноября будет перезаписана заявкой на B 8 ноября, и подтверждение первой забронирует неверный вариант; следовательно, одного `user_id` тоже недостаточно. |
| **6. Устаревший вариант.** | Только успешный ответ `reserve_room` создаёт бронь и завершает A2A Task; `occupied` очищает предложение, возвращает фазу поиска и требует нового подтверждения замены. Альтернатива — завершать задачу после любого ответа операции. Тогда отказ для `A-101` будет выдан как бронь либо `A-102` будет забронирована без согласия пользователя. **Трасса:** taskId `c7bf0bc7-5924-474f-9042-673612149ae0`; строки 12 (`mcp.tool.call`, `occupied`) и 13 (`mcp.tool.call`, новый поиск). |

**Вывод.** A2A связывает пользовательские сообщения с Task, а MCP предоставляет ресурсы и операции над внешним состоянием. Для корректного продолжения нужны самостоятельные снимки, явное происхождение долговременной памяти и переходы автомата, основанные на фактическом ответе операции.
