# Обязательная лабораторная. Бюро бронирования

**MCP, A2A, состояние и память. Индивидуально. Вся работа сдаётся через 14 дней после выдачи, без защиты.**

Вы помогаете провести семинар. Агент подобрал аудиторию, но пользователь уточнил условия, вернулся в новом диалоге или подтвердил предложение после перезапуска процесса. Иногда предложенную аудиторию уже успели занять. Нужно определить правила, при которых система продолжает именно нужную задачу и сообщает фактический результат.

В работе **пять небольших функций и шесть обязательных сценариев**. Серверы, протоколы, база, автомат агента и проверки готовы. Меняется только `lab/policy.py`. Объём рассчитан на работу в пределах четырёх часов; отчёт занимает 1–2 страницы. Дополнительных заданий нет.

Для каждой ситуации вы формулируете правило, реализуете его и объясняете, почему другое правдоподобное правило приводит к ошибке. Прохождение проверок подтверждает поведение программы; обоснование решения входит в оценку отдельно.

## Готовая система

```text
Координатор (готовый сценарий)
  │ A2A: Agent Card → SendMessage → Task → GetTask
  ▼
Агент бронирования (отдельный процесс)
  │ MCP: обнаружение возможностей, чтение профиля, поиск и бронь
  ▼
MCP-сервер (отдельный процесс)
  └─ SQLite: предпочтения, занятость и записи учебных броней

Агент отдельно хранит прикладные снимки задач и протокольные A2A Task.
```

Бронирования учебные. Все обязательные сценарии работают локально через `127.0.0.1`, без LLM, ключей API, GPU и Docker. После установки зависимостей интернет не нужен. Координатор подаёт фиксированные структурированные заявки: качество распознавания свободного текста не влияет на оценку.

Каркас использует официальные Python SDK `mcp==2.3.0` и `a2a-sdk==1.2.2`; согласованные версии протоколов — MCP 2026-07-28 и A2A 1.0. Структурированные сообщения A2A передаются в `Part.data`. Результат завершённой задачи передаётся также в артефакте.

## Запуск

Требуется **Python 3.12 или 3.13**. Распакуйте архив и откройте терминал в папке с `run_lab.py`.

Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run_lab.py
```

macOS / Linux:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python run_lab.py
```

Далее `python` означает Python созданного окружения. Можно продолжать использовать полный путь из команд выше; при установленном Python 3.13 замените номер версии в команде создания окружения.

Исходный каркас должен дать **0/6**: пять функций запускаются, но содержат ошибки. Сообщения `FAIL` показывают нарушенное свойство. `Ошибка запуска или реализации` означает исключение; подробности — в `runs/<запуск>/scenario_N/mcp.log` и `a2a.log`. Каждый сценарий использует отдельную чистую базу.

## План работы

1. Прочитайте шесть ситуаций ниже и запишите для каждой предварительное правило одной фразой. Это черновик будущего отчёта, отдельно сдавать его не нужно.
2. Запустите исходный пример и `python run_lab.py --inspect`. Найдите skill агента в Agent Card, операции `search_rooms`, `reserve_room`, `save_preference`, ресурс `rules://booking` и шаблон `profile://{user_id}`. Определите границу между обращением к исполнителю и вызовом операции.
3. Прочитайте форматы данных и пять функций в `lab/policy.py`. Исправьте правила, сохранив сигнатуры. Для понимания вызовов достаточно `lab/runtime.py`; писать серверы и разбирать весь SDK не требуется.
4. Проверяйте отдельные ситуации, например `python run_lab.py --scenario 2`, затем весь набор: `python run_lab.py`. Сопоставляйте сообщения проверки со своим правилом.
5. Заполните шесть коротких разборов в `report_template.md`. Для перезапуска и занятой аудитории используйте трассы. Соберите один архив для сдачи.

## Шесть ситуаций для исследования

| № | События и требуемое поведение | Решение, которое нужно обосновать |
|---|---|---|
| 1 | В заявке не хватает времени. Пользователь сообщает только время; остальные условия остаются в силе. Продолжается исходная Task. | Как трактовать неполное сообщение? Почему уточнение передаётся по A2A, а поиск аудитории выполняется через MCP? |
| 2 | Агент уже предложил аудиторию и остановлен до подтверждения. Новый процесс должен продолжить ту же задачу и сохранить предложенный вариант. | Что обязан содержать самостоятельный снимок? Какие сведения нельзя восстановить из одного идентификатора? |
| 3 | Пользователь явно просит запомнить предпочтение корпуса B. После перезапуска начинается новая Task с новым контекстом; предпочтение доступно без старого диалога. | На каком основании сведения становятся долговременной памятью? Как различать источник записи и текущую задачу? |
| 4 | В памяти предпочтение B, а для этой встречи пользователь просит A. Требуется аудитория в A; следующая независимая заявка по-прежнему может использовать B. | Как согласовать память и текущую просьбу? Как отличить разовое исключение от изменения предпочтения? |
| 5 | Перемешаны обращения двух пользователей и двух задач одного пользователя. Две задачи могут иметь один contextId. Каждое подтверждение относится к своему предложению. | Как выбрать область действия ключа состояния? Какое другое правило смешает независимые задачи? |
| 6 | Аудиторию заняли после предложения, но до подтверждения. Инструмент отвечает об отказе; агент предлагает замену и ждёт нового подтверждения. | Как ответ операции меняет состояние задачи? Почему получение ответа и достижение цели оцениваются отдельно? |

Контрпример в отчёте — **короткое мысленное развитие одной из этих ситуаций**: конкретные входные данные или порядок событий и неправильный результат альтернативного правила. Писать новые сценарии или проводить дополнительные эксперименты не требуется. Контрпример может опираться на имеющийся прогон, но должен объяснять причину ошибки.

## Форматы данных и границы решений

Форматы ниже задаёт готовая инфраструктура. По ситуациям выше нужно определить правила объединения, хранения и продолжения. Их способ реализации вы выбираете сами. Все пять функций возвращают независимые данные и не изменяют аргументы; доступен `deepcopy` из стандартной библиотеки.

| Функция | Вход и ожидаемый вид результата |
|---|---|
| `compose_requirements(current, patch, memory)` | Известные условия задачи, новые явно указанные поля и профиль пользователя → словарь условий текущей задачи. |
| `memory_to_save(existing, remember, source_message_id)` | Прежняя запись профиля, отдельное указание о запоминании либо `None`, ID входящего сообщения → запись профиля. |
| `checkpoint_key(user_id, task_id)` | Идентификаторы владельца и задачи → стабильная строка ключа. |
| `checkpoint_to_save(state)` | Состояние автомата → самостоятельный снимок из выбранных полей `state`. Имена полей и их значения сохраняются. |
| `after_reservation(state, result)` | Состояние перед бронированием и ответ операции → обновлённое состояние того же формата. |

**Условия заявки.** Допустимые поля: `date` (YYYY-MM-DD), `time` (HH:MM), `people` (положительное целое), `projector` (bool), `building` (`A` или `B`). `patch` содержит только сообщённые поля. Отсутствие поля отличается от явного `False`. Если проектор не запрошен, его наличие не ограничивает поиск — значение по умолчанию `False`. Без корпуса поиск ведётся в обоих корпусах. Дата, время и число участников обязательны перед поиском.

**Профиль.** В этой работе между задачами переносится только предпочтение корпуса. Формат записи: `building`, `source_message_id` (ID сообщения, на котором основана запись), `revision` (счётчик принятых явных указаний о запоминании). Первое принятое указание имеет номер 1; каждое следующее увеличивает счётчик на один, даже если корпус повторён. Указание `remember` допустимо, когда содержит `building` со значением `A` или `B`. Отсутствующая, пустая или недопустимая инструкция не является новым указанием. Эти соглашения нужны для проверки происхождения записи; они не определяют, как применять профиль к текущей заявке.

**Идентификаторы.** Входы функции ключа — непрозрачные строки, в том числе с `:`, `/` и другими разделителями. Контракт действует для любых пар входов: одинаковая пара обозначает одну запись, различающиеся пары — разные. Нельзя полагаться на случайное отсутствие совпадений в примерах. `contextId` объединяет взаимодействия; конкретная Task имеет свой `taskId`.

**Поля состояния автомата:**

| Поле | Значение |
|---|---|
| `user_id` | Владелец заявки. |
| `task_id` | Прикладная связь с протокольной задачей. |
| `context_id` | Контекст взаимодействия. |
| `requirements` | Условия текущей заявки. |
| `phase` | Этап обработки, значения описаны ниже. |
| `proposal` | Предложенная аудитория с характеристиками, либо `None`. |
| `reservation` | Полученный результат бронирования, либо `None`. |
| `chat` | Диагностический журнал входящих сообщений в живом процессе. |
| `cache` | Последняя поисковая выдача, которую можно получить заново. |

Снимок должен быть самостоятельной записью для продолжения и разбора задачи: по нему устанавливаются владелец и связь с взаимодействием, восстанавливаются условия, точка продолжения и сведения о предложении или уже полученном результате. Для этого нельзя рассчитывать на следующее сообщение, повторный поиск или разбор переписки. Схема снимка одинакова до и после завершения; отсутствие значения представляется `None`. Диагностика и повторно вычисляемые данные не должны разрастаться в снимке. Выберите поля и обоснуйте выбор в разборе сценария 2.

Значения `phase` заданы автоматом: `search` — требуется подбор; `need_input` — недостаёт обязательных условий либо вариантов нет и нужны другие условия; `waiting_confirmation` — есть актуальное предложение, ожидается согласие; `completed` — получен подтверждённый результат бронирования. Фазы не переименовываются. Остальные поля задачи сохраняют смысл при переходах; устаревший вариант нельзя выдавать за актуальное предложение.

После успешного завершения допустимо сохранить подтверждённый вариант в `proposal` как сведения о выборе либо очистить это поле. Оба решения принимаются проверками. Фактическое подтверждение хранится в `reservation`; подмена выбранного варианта другим не допускается.

В `after_reservation` журнал `chat` сохраняется: его ведёт инфраструктура. Кеш можно оставить прежним либо очистить до `{}`. Новую поисковую выдачу формирует готовый поиск; самостоятельно наполнять кеш не требуется.

**Ответ операции.** `reserve_room` возвращает либо `{"ok": true, "reservation": {...}}`, либо `{"ok": false, "reason": "occupied"}`. Поля подтверждения: `id`, `room_id`, `date`, `time`, `user_id`. Операция сообщает факт о мире; сведения о бронях нельзя придумывать. После перехода в подбор готовый автомат выполняет новый поиск и формирует предложение.

A2A Task хранится отдельно. `GetTask` позволяет наблюдать её статус и артефакт, но автомат восстанавливается из прикладного снимка. Его локальные `active` и `cache` исчезают при перезапуске; сохранённая протокольная история не используется им как запасной способ восстановления.

## Что проверяет запуск

Те же шесть сценариев проверяют наблюдаемое поведение и контракты пяти функций: смысл частичных сообщений, явные значения, происхождение памяти, изоляцию, самостоятельность снимка и отсутствие изменения аргументов. В исходниках проверок нет ограничений на конкретный алгоритм или способ кодирования ключа.

Во втором сценарии действительно меняется процесс и PID. В шестом проверочный стенд добавляет внешнюю бронь между предложением и подтверждением. Поля результата, статуса и артефакта A2A сверяются с SQLite, условиями задачи и подтверждённым предложением. Исправленный вариант должен получить 6/6.

## Как читать трассу

В `runs/<запуск>/scenario_N/trace.jsonl` каждая строка — отдельный JSON-объект. Поле `event` задаёт событие.

| Событие | Содержимое |
|---|---|
| `mcp.discover`, `mcp.resource.read` | Возможности сервера, прочитанные правила или профиль. |
| `a2a.card`, `a2a.send` | Карточка агента, `messageId`, `taskId`, `contextId`, структурированная заявка. В первой отправке taskId назначает сервер. |
| `mcp.tool.call` | Имя операции, аргументы и фактический ответ, в том числе `ok: false`. |
| `a2a.result`, `a2a.get` | Состояние Task, данные результата и содержимое артефактов. |
| `agent.restart` | `old_pid`, `new_pid` и путь сохранённой базы. |

Прикладная `phase` и протокольная `a2a_state` отвечают на разные вопросы. В каркасе и уточнение данных, и ожидание подтверждения представлены как `TASK_STATE_INPUT_REQUIRED`; результат завершённой задачи — как `TASK_STATE_COMPLETED`.

Обычно достаточно трёх коротких предложений, около 50–70 слов. Для сценариев 2 и 6 дополнительно укажите taskId и номера двух ключевых строк трассы с названиями событий. В сценариях 1, 2 и 6 пояснение должно показывать роль протокола и прикладной логики.

Всего 1–2 страницы, **без титульного листа, ФИО и раздела о личном вкладе**. Отдельная таблица хранения данных, дополнительные эксперименты и новые тесты не нужны.

Через 14 дней после выдачи сдайте один ZIP:

- исправленный `policy.py`;
- `report.md` или PDF с шестью разборами;
- `results.json` последнего полного запуска;

**10 баллов:** 6 — за шесть сценариев (по одному); 2 — за объяснение границы MCP/A2A, идентификаторов и соответствующие контрпримеры; 2 — за обоснование правил состояния и памяти, контрпримеры и свидетельства из трасс. В четырёх баллах за объяснения оцениваются корректность собственного правила, правдоподобность альтернативы и причинная связь между конкретным примером и ошибкой. Фраза «тест прошёл» без такого разбора обоснованием не является. Проверка кода выполняется на исходной инфраструктуре с вашим `policy.py`.

## Границы учебной системы

`user_id` задаёт доверенный локальный стенд: разделение данных здесь не является реализацией авторизации. Слоты сравниваются как точные пары `(date, time)`; произвольные пересечения интервалов не моделируются. Работать над этими ограничениями не требуется.

Готовый режим с LLM включается командой `python run_lab.py --chat` и не участвует в оценивании. Для уже доступной модели задайте `LLM_BASE_URL` с `/v1`, `LLM_MODEL` и, если требуется, `LLM_API_KEY`. Модель извлекает поля короткой реплики, затем они проверяются по схеме и передаются в тот же A2A/MCP-контур. Команды: `/confirm`, `/new`, `/exit`. По умолчанию обращений к модели нет; настраивать её для сдачи не нужно.

Справка: [Python SDK MCP](https://github.com/modelcontextprotocol/python-sdk), [Python SDK A2A](https://github.com/a2aproject/a2a-python), [жизненный цикл A2A Task](https://a2a-protocol.org/latest/topics/life-of-a-task/). Используйте версии из `requirements.txt`.
