# ЛР9. Бюро выдачи оборудования

## Запуск

Python 3.12.14; Qwen2.5-1.5B-Instruct, GGUF Q4_K_M; llama.cpp build 12555. Модель доступна без ключа; URL весов, SHA-256 и настройки приведены в `model.json`. Для работы кода лабораторной сторонние Python-зависимости не нужны. После загрузки GGUF и сборки или установки `llama-server` в первом терминале:

```bash
llama-server -m /path/to/qwen2.5-1.5b-instruct-q4_k_m.gguf \
  --host 127.0.0.1 --port 8080 --alias qwen25-1.5b \
  -c 2048 -ngl 999 -np 1
```

Для CPU вместо `-ngl 999` использовать `-ngl 0`. В другом терминале, из корня архива:

```bash
export MAS_LLM_URL=http://127.0.0.1:8080/v1
export MAS_LLM_MODEL=qwen25-1.5b
export MAS_LLM_TIMEOUT=120
unset MAS_LLAMA_COMPLETION MAS_LLAMA_GGUF
python -m lab.model
python -m lab.public_tests --timeout 420 --report public_results.json
python -m lab.cli --state-dir ./state
```

CLI принимает по одной JSON-строке на ход с `request_id`, `message_id` и `text`. Файл `model.json` описывает использованную конфигурацию; клиент получает настройки из переменных окружения или аргументов CLI, а не загружает этот файл автоматически.

## Агенты и правила

Первый агент выбирает код видеовыхода; допустимые варианты ответа ограничены грамматикой. Код проверяет предложение по данным сообщения с учётом отрицания, неопределённости и предыдущей заявки. Подбор идёт по `video_in`, `video_out`, `available` и явному требованию к входу проектора; `note` не определяет совместимость. Изменение условий сбрасывает прежнее предложение. Запись разрешена только после распознанного подтверждения текущего комплекта; при потере наличия возвращается `unavailable` без автоматического бронирования замены.

Второй агент выбирает одну из двух формулировок уже установленного статуса. Код подставляет реальные идентификаторы оборудования и полученный от симулятора ID брони. Произвольные инструкции в сообщении или описании оборудования не являются разрешением на бронь.

## Восстановление и результаты

Состояние каждой заявки хранится в JSON-файле в каталоге состояния; имя основано на SHA-256 от `request_id`, а запись заменяется атомарно. При временном `TemporaryError` выполняется повторное чтение каталога. Перед обработкой проверяется фактическая бронь симулятора; операция имеет стабильный ключ идемпотентности.

Открытые тесты с реальной моделью: **качество 8/8, восстановление 3/3** (`public_results.json`). В трёх сценариях восстановления:

1. После перезапуска до подтверждения восстановлено предложение и забронирован тот же комплект.
2. После временной ошибки каталог успешно прочитан повторно и сформировано предложение.
3. После падения между записью брони и отправкой ответа повтор сообщения вернул прежний ID; в симуляторе осталась одна бронь.

Дополнительно прошли 15 групп защитных тестов, 79 адаптированных внешних сценариев и 12 дополнительных сценариев с отдельными эталонами порта и состояния базы. Их использовали при доработке, а часть проверок текста ответа носит эвристический характер: это не независимая оценка закрытых атак. Адаптации и ограничения описаны в `external_scenarios/README.md`.
