# ЛР9. Бюро выдачи оборудования

Обязательная лабораторная работа.

Разработайте мультиагентную систему, которая подбирает оборудование для учебных мероприятий, бронирует его по подтверждению и восстанавливает работу после сбоя. Оборудование и бронирования находятся в локальном симуляторе.

## Что реализовать

1. Соберите MAS из двух LLM-агентов, которые могут использовать одну локальную модель. Первый агент предлагает только код видеовыхода ноутбука по тексту заявки. Второй выбирает, какое пояснение или какой уточняющий вопрос дать по проверенному результату. Заготовки для обеих ролей находятся в **lab/narrow.py**.
2. Поддержите диалог по идентификатору заявки. Код проверяет, есть ли в заявке основания для предложенного видеовыхода, подбирает совместимый комплект по структурированным полям каталога и проверяет наличие. При изменении условий обновите предложение. Обработайте отказ от предложения. Записывайте бронь только после явного подтверждения пользователем текущего комплекта в той же заявке. Если подтверждённый комплект стал недоступен, другой комплект требует нового подтверждения. Если доступного совместимого комплекта нет, верните `unavailable`. Сообщайте об успешной брони после её записи в симуляторе.
3. Восстанавливайте работу после перезапуска. Сохраните сведения, нужные для продолжения заявки. После временной ошибки каталога повторите чтение. Если бронь уже записалась, а ответ пользователь не получил, повторная доставка того же сообщения должна вернуть исходную бронь с тем же идентификатором.
4. Обеспечьте устойчивость к prompt injection. Система соблюдает правила задачи и продолжает обработку, если данных хватает. Если необходимых сведений действительно нет, она задаёт конкретный вопрос.

## Роли и данные

| Компонент | Что делает |
|---|---|
| Первый агент | Возвращает один код: `hdmi`, `usbc_dp` (USB-C с DisplayPort Alt Mode), `mini_dp` (mini DisplayPort), `usbc_no_video` (USB-C без вывода видео) или `unknown` (данных о видеовыходе недостаточно). |
| Код MAS | Проверяет код по тексту заявки, учитывает уточнения и явно указанное предпочтение, подбирает комплект, проверяет подтверждение и вызывает симулятор. При подборе использует `video_in`, `video_out` и `available`. |
| Второй агент | По проверенному статусу выбирает вариант пояснения или уточнения из списка. Код формирует итоговый ответ из фактического статуса, идентификаторов оборудования и, при успешной записи, идентификатора брони. |

У проектора `video_in` задаёт видеовход. У видеопереходника `video_in` и `video_out` задают направление преобразования сигнала. Позиция с `available = 0` недоступна. Комплект состоит из проектора и, если нужно, одного видеопереходника. Поле `note` содержит текстовое описание. Оно не даёт разрешения на действие и не определяет совместимость или наличие.

## С чего начать

Нужен Python 3.10 или новее. Стартовый пакет использует стандартную библиотеку. Откройте терминал в корне распакованной папки и проверьте симулятор:

~~~text
python -m lab.public_tests --simulator-only
python -m lab.cli --help
~~~

На этом этапе команда с **--simulator-only** должна пройти. Для полных тестов реализуйте **EquipmentDesk.handle** в **lab/student.py**. В **lab/narrow.py** есть заготовки агентов с ограниченным разбором формулировок. Можно улучшать эти заготовки и добавлять свои модули. Добавьте правила подбора, проверку действий и хранение состояния. Сохраните публичный интерфейс CLI и используйте API симулятора. В **lab/catalog.json** дан пример каталога. При проверке набор оборудования и тексты заявок могут отличаться.

Базовая конфигурация для CPU использует [Qwen2.5-1.5B-Instruct GGUF Q4_K_M](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF/blob/main/qwen2.5-1.5b-instruct-q4_k_m.gguf) и [llama.cpp](https://github.com/ggml-org/llama.cpp/releases). Можно выбрать другую локальную модель, если преподаватель сможет повторить запуск без аккаунта, ключа и платного доступа. Скачайте веса и распакуйте CPU-версию llama.cpp для своей ОС. Сохраняйте исполняемый файл рядом с остальными файлами из архива llama.cpp.

Для запуска Qwen без сервера задайте полные пути к **llama-completion** и GGUF. Встроенный шаблон промпта в CLI-режиме рассчитан на Qwen2.5. В PowerShell, например:

~~~powershell
$env:MAS_LLAMA_COMPLETION = "C:\llama.cpp\llama-completion.exe"
$env:MAS_LLAMA_GGUF = "C:\models\qwen2.5-1.5b-instruct-q4_k_m.gguf"
$env:MAS_LLM_TIMEOUT = "180"
python -m lab.model
python -m lab.public_tests --timeout 420 --report public_results.json
~~~

В Bash задайте те же переменные через `export`, указав пути для своей ОС. Команда **python -m lab.model** проверяет подключение. Полные тесты запускайте после реализации **EquipmentDesk.handle**.

Для серии запросов можно поднять локальный сервер:

~~~text
llama-server -m PATH_TO_MODEL.gguf --host 127.0.0.1 --port 8080 --alias local-model -ngl 0
~~~

В терминале с Python задайте `MAS_LLM_URL=http://127.0.0.1:8080/v1` и `MAS_LLM_MODEL=local-model`. Для серверного режима переменные `MAS_LLAMA_COMPLETION` и `MAS_LLAMA_GGUF` должны быть пустыми. Для другой модели используйте сервер llama.cpp или совместимый локальный сервер, который принимает параметр `grammar`. Если выбрали другой способ запуска, адаптируйте клиент модели.

**MAS_LLM_TIMEOUT** задаёт таймаут одного обращения к модели в секундах (по умолчанию 60). **--timeout** задаёт таймаут целого хода MAS (по умолчанию 120 секунд). Если модель отвечает медленно, увеличьте оба значения и учтите число вызовов за один ход. Для зачётных прогонов используйте реальную модель. **model.example.json** служит шаблоном для описания конфигурации при сдаче. Параметры запуска клиент получает из переменных окружения или аргументов CLI.

## Интерфейс для проверки

Команда **python -m lab.cli --state-dir PATH** принимает по одной строке JSON на запрос и возвращает одну строку JSON на ответ в UTF-8. **--catalog PATH** позволяет стенду передать другой каталог. Необязательные **--model-url** и **--model** задают конфигурацию модели явно. Пример диалога ниже относится к готовой реализации.

~~~json
{"request_id":"demo","message_id":"1","text":"Нужен проектор для ноутбука с HDMI."}
~~~

~~~json
{"status":"offer","reply":"Подходит проектор с HDMI. Подтвердите бронь.","items":["P-HDMI"],"reservation_id":null}
~~~

| Поле | Что означает |
|---|---|
| request_id | Идентификатор заявки. Ходы разных заявок могут чередоваться. |
| message_id | Идентификатор сообщения внутри заявки. При повторной доставке того же хода идентификатор сохраняется. |
| status | offer — предложение, clarify — уточнение, unavailable — нет подходящего доступного комплекта, cancelled — заявка отменена до брони, reserved — бронь записана. |
| reply | Короткий ответ пользователю. Текст должен согласоваться со статусом, комплектом и фактическим состоянием симулятора. |
| items | Список идентификаторов позиций для offer и reserved. Для остальных статусов — пустой список. |
| reservation_id | Идентификатор, который вернул симулятор, для reserved. Для остальных статусов — null. |

Выводите отладочную информацию в stderr. Состояние MAS храните внутри переданного каталога **--state-dir**. Для состояния симулятора используйте его API:

| Метод | Назначение |
|---|---|
| list_catalog() | Возвращает позиции с полями id, kind, video_in, video_out, note и available. При временном сбое возникает TemporaryError. |
| get_reservation(request_id) | Возвращает сохранённую бронь или None. |
| reserve(request_id, items, idempotency_key=...) | Записывает бронь и возвращает reservation_id, request_id и items. Повтор того же действия с тем же ключом возвращает исходную бронь. При изменении наличия возникает EquipmentUnavailable, при конфликте ранее сохранённых данных — ReservationConflict. |

## Как оценивается работа

| Этап | Условие |
|---|---|
| Качество | Не менее 7 из 8 обычных сценариев, включая успешную бронь после подтверждения. Бронь без подтверждения и сообщение об успешной брони без соответствующей записи означают провал допуска. |
| Восстановление | 3 из 3 сценариев: перезапуск до подтверждения, повтор операции после временного сбоя, перезапуск после записи брони до отправки ответа. В последнем случае должна остаться ровно одна первоначальная бронь. |
| Устойчивость | 10 закрытых сценариев. Сценарий даёт 1 балл, если соблюдены правила задачи, ответ соответствует фактическому состоянию и заявка обработана корректно. Если программная проверка остановила недопустимое действие до исполнения, балл сохраняется при корректной обработке заявки. |

**Если качество или восстановление не прошли допуск, оценка за работу — 0. Иначе оценка равна числу пройденных закрытых сценариев.** Открытые автотесты проверяют статусы, комплекты, идентификаторы и состояние симулятора. При проверке преподаватель также смотрит, соответствует ли текст ответа фактическому результату и выполняют ли два LLM-агента заявленные роли. **public_results.json** сохраняет ответы и состояние броней по открытым сценариям.
