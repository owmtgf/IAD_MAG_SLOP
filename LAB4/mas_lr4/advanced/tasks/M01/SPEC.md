# M01 — обработка событий заказа

Исправьте существующую реализацию `starter/app`. Публичная функция —
`app.api.solve(data)`. Она принимает словарь и возвращает JSON-совместимый
словарь. Каждый вызов полностью независим: состояние не сохраняется между
вызовами, входной объект изменять нельзя. Используйте только Python 3.11+
и стандартную библиотеку. Менять можно только файлы, перечисленные в
`task.json`; интерфейс и видимые тесты менять нельзя.

Это последовательный сервис заказов: резервирование товара, платежи,
отгрузка, отмена неотгруженных единиц и возвраты. События могут приходить
повторно или до создания заказа. Переставлять события и откладывать их
обработку нельзя. Внешних сервисов, времени, потоков и случайности нет.

## Вход

```json
{
  "stock": {"book": 5},
  "events": [
    {"id": "e1", "type": "place", "order_id": "a", "sku": "book", "qty": 2, "unit_price": 5},
    {"id": "e2", "type": "pay", "order_id": "a", "amount": 10},
    {"id": "e3", "type": "ship", "order_id": "a", "qty": 1}
  ]
}
```

Гарантии для всех тестов: `stock` содержит 1–4 SKU с целым остатком 0–50;
`events` содержит 0–30 событий. Идентификаторы — непустые строки ASCII,
регистр значим. `type` — один из пяти типов ниже. Все обязательные поля
присутствуют, типы корректны, лишних полей нет, кроме необязательного
`fail_at`. `qty` — целое 1–20, `unit_price` и `amount` — целые 1–1000.
SKU в `place` может отсутствовать в `stock`, а `order_id` может еще не
существовать: это обычные отклоняемые события. Невалидный JSON и другие
нарушения этих гарантий не проверяются. Все суммы — целые денежные единицы;
налогов, комиссий, дробных сумм и округления нет.

## Состояние заказа

При создании фиксируются `sku`, исходное количество `qty` и `unit_price`.
Заказ не удаляется даже после полной отмены или отгрузки. Его поля:

| Поле | Значение |
|---|---|
| `shipped` | Накопленное число отгруженных единиц |
| `cancelled` | Накопленное число отмененных единиц |
| `paid` | Сумма всех успешно проведенных платежей (брутто) |
| `refunded` | Сумма всех успешно проведенных возвратов, включая автоматические |
| `reserved` | `qty - shipped - cancelled` |
| `net_paid` | `paid - refunded` |

Активное количество равно `qty - cancelled`; стоимость активной части
равна этому количеству, умноженному на цену. `stock` всегда обозначает
доступный для **нового** резервирования товар. При отгрузке товар уже был
зарезервирован и доступный остаток не меняется. При отмене товар возвращается
в доступный остаток. Стоимость отгруженных единиц должна оставаться оплаченной.

## Обработка и порядок проверок

Перед любыми проверками событие с ранее встречавшимся `id` получает статус
`duplicate` и ничего не меняет. Идентичность задается только `id`, глобально
для всех заказов и типов. Измененный payload тоже считается дубликатом.
Первое событие занимает `id` при любом исходе: `applied`, `rejected` или
`failed`. Повторная попытка требует нового `id`. Порядок результатов
совпадает с порядком входных событий.

Правила применяются в следующем порядке; первая нарушенная проверка задает
`reason`. Положительность чисел уже гарантирована входным контрактом.

| Тип и дополнительные поля | Проверки по порядку | Успешное действие |
|---|---|---|
| `place`: `sku`, `qty`, `unit_price` | Заказ уже существует → `order_exists`; неизвестный SKU → `unknown_sku`; `qty > stock[sku]` → `out_of_stock` | Списать `qty` из доступного остатка; создать заказ с нулевыми счетчиками. Равенство остатка и количества допустимо. |
| `pay`: `amount` | Неизвестный заказ → `unknown_order`; активное количество = 0 → `inactive_order`; `net_paid + amount` больше стоимости активной части → `overpayment` | Увеличить `paid`, добавить запись платежа. После возврата допускается повторная оплата в пределах текущего нетто-лимита. |
| `ship`: `qty` | Неизвестный заказ → `unknown_order`; `qty > reserved` → `quantity_exceeded`; `net_paid < (shipped + qty) * unit_price` → `not_paid` | Увеличить `shipped`, добавить запись отгрузки; доступный остаток не изменять. |
| `cancel`: `qty` | Неизвестный заказ → `unknown_order`; `qty > reserved` → `quantity_exceeded` | Увеличить `cancelled`, вернуть `qty` в доступный остаток. Затем автоматически вернуть `max(0, net_paid - (qty_исходное - cancelled_новое) * unit_price)`. |
| `refund`: `amount` | Неизвестный заказ → `unknown_order`; `amount > net_paid - shipped * unit_price` → `refund_exceeded` | Увеличить `refunded` и добавить запись возврата. Резерв и количество не меняются. |

Автоматический возврат в `cancel` использует **новое** значение `cancelled`
и нетто-сумму до этого автоматического возврата. Если возврат нулевой,
запись в денежный журнал не добавляется. Других автоматических платежей
или возвратов нет. Полная отмена оплаченного заказа возвращает все его
нетто-средства. После полной отгрузки пополнения и ручные возвраты фактически
ограничены теми же формулами; отдельного статуса «закрыт» нет.

## Инъекция сбоя и атомарность

`fail_at`, если задан, принимает одну из разрешенных для типа строк:

| Тип | Контрольная точка |
|---|---|
| `place` | `after_stock`: после уменьшения остатка и создания заказа |
| `pay` | `after_ledger`: после изменения `paid` и денежной записи |
| `ship` | `after_shipping`: после изменения `shipped` и записи отгрузки |
| `cancel` | `after_stock`: после изменения `cancelled` и остатка; `after_refund`: после полного автоматического возврата, даже если он нулевой |
| `refund` | `after_ledger`: после изменения `refunded` и денежной записи |

Если событие прошло проверки и достигло указанной точки, оно получает
`failed` с причиной `injected_failure`. **Все** изменения этого события
откатываются: остаток, существующий или новый заказ, денежный журнал,
журнал отгрузок. Идентификатор остается занятым и результат остается
в журнале результатов. Отклоненное событие не достигает контрольных точек:
его статус — `rejected`, даже при наличии `fail_at`. Дубликат также не
запускает обработчик и не вызывает сбой. Обычное отклонение ничего не меняет.

## Выход

Возвращаются ровно пять полей:

* `stock`: доступные остатки всех исходных SKU, включая нулевые.
* `orders`: словарь всех успешно созданных заказов по `order_id`. Каждый
  содержит ровно `sku`, `qty`, `unit_price`, `shipped`, `cancelled`, `paid`,
  `refunded`, `reserved`, `net_paid`.
* `ledger`: записи в порядке проведения: `event_id`, `order_id`, `kind`
  (`payment` или `refund`), `amount`, `source` (`pay`, `refund` или `cancel`).
* `shipments`: записи успешных отгрузок в порядке проведения: `event_id`,
  `order_id`, `qty`.
* `results`: одна запись на каждое входное событие: `event_id`, `status`.
  Только при `rejected` и `failed` есть дополнительное поле `reason`.

Порядок ключей словарей несущественен; порядок элементов списков значим.
Для приведенного входа остаток равен 3, заказ имеет `shipped=1`,
`reserved=1`, `paid=10`, `refunded=0`, `net_paid=10`; в денежном журнале один
платеж на 10, в отгрузках одна запись на 1, все три результата — `applied`.
