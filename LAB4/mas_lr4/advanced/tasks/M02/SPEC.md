# M02 — Детерминированный планировщик рабочих процессов

Исправьте реализацию в `starter/app`. Входная точка: `app.api.solve(data)`.
Она принимает JSON-объект и возвращает JSON-объект. Каждый вызов полностью
изолирован: часы, задания, снимки, очереди и ошибки не переносятся между вызовами.
Можно менять любые перечисленные в `task.json` файлы Python. Стандартной библиотеки
достаточно; сеть, внешние зависимости и изменение тестов не требуются.

## Вход

`{"jobs": [...], "events": [...]}`. `events` необязателен, по умолчанию `[]`.
Начальные задания корректны: не больше 12, уникальные непустые строковые `id`,
существующие зависимости без циклов и самозависимостей. Пустой список допустим.
Задание имеет только следующие поля:

| Поле | Значение и значение по умолчанию |
|---|---|
| `id` | Непустая строка, обязательно |
| `deps` | Список уникальных `id`, по умолчанию `[]` |
| `resources` | Список уникальных непустых строк, по умолчанию `[]` |
| `priority` | Целое от −9 до 9, по умолчанию 0; больше означает раньше |
| `duration` | Целое от 1 до 9, по умолчанию 1; число тактов на попытку |
| `failures` | Целое от 0 до 9, по умолчанию 0; первые столько попыток каждой версии завершаются неудачно |
| `max_retries` | Целое от 0 до 9, по умолчанию 0; число дополнительных попыток после первой |

Имена сравниваются обычным порядком строк Python, регистр значим. Порядок заданий,
зависимостей и ресурсов во входных списках не влияет на результат. Событий не больше
30. События могут быть некорректны; для них определены ошибки ниже. Значения JSON
`true`/`false` не считаются целыми числами. Все строки и списки обычные JSON-значения.

## Начальное состояние и запуск

Время равно 0, счетчик `next_ticket` равен 0. У каждого задания `version=1`,
`state="blocked"`, `attempts=remaining=0`, `ticket=completed_at=null`,
`dep_versions={}`. Ресурсы эксклюзивны; один ресурс занят максимум одним заданием.
Необъявленные заранее имена ресурсов разрешены. Безресурсные задания не ограничены
по числу одновременных запусков.

Сразу после инициализации выполняется процедура запуска. Та же процедура выполняется
после каждого отдельного такта, успешного `cancel` и успешного `revise`:

1. Обойти задания по `id`. Каждое `blocked`, у которого **все** зависимости имеют
   состояние `succeeded`, перевести в `ready` и присвоить текущий `next_ticket`,
   затем увеличить счетчик на 1. Пустой список зависимостей удовлетворен.
   Другие состояния не меняются на этом шаге. Неудача предка оставляет потомка
   `blocked`; автоматического распространения состояния `failed` нет.
2. Просмотреть все `ready` по ключу `(-priority, ticket, id)`. Локальное множество
   резервов сначала пустое и существует только в рамках этого обхода.
3. Если хотя бы один требуемый ресурс занят выполняющимся заданием **или** входит
   в резервы, задание остается `ready`, **не захватывает ни одного ресурса**, а
   **все** его требуемые ресурсы добавляются в резервы. Это правило запрещает
   позднему заданию обойти более раннего ожидающего на общем ресурсе, даже если
   этот общий ресурс свободен, а раннее задание ждет другой ресурс. Задание с
   непересекающимися ресурсами может запуститься.
4. Иначе задание атомарно захватывает все ресурсы, становится `running`, теряет
   билет (`ticket=null`), увеличивает `attempts` на 1, получает `remaining=duration`
   и записывает текущие версии зависимостей в `dep_versions` (ключи по `id`).
   В историю добавляется `start`.

Часы меняются только при `tick` и `restore`. Запуск, отмена и обновление времени
не прибавляют. Билет сохраняется, пока задание ожидает ресурсов; новая попытка
получает новый билет и конкурирует заново. Счетчик билетов начинается с 0.

## События

### `{"op":"tick", "steps":N}`

`steps` необязателен, по умолчанию 1; допустимы целые 1…5. Лишние поля запрещены.
Выполнить N отдельных тактов. Один такт сначала увеличивает время на 1, затем
уменьшает `remaining` **всех** уже выполняющихся заданий на 1. После этого обработать
задания с нулевым остатком по `id`; все завершения происходят до новых запусков.
Освободить все ресурсы завершившегося задания.

Если `attempts <= failures`, попытка неудачна. Когда `attempts <= max_retries`,
задание возвращается в `blocked`, `dep_versions={}`, в историю пишется `retry`.
Иначе состояние `failed`, `dep_versions={}`, запись `failed`. Таким образом при
`max_retries=1` допускаются попытки 1 и 2. При успехе состояние `succeeded`,
`completed_at` равно текущему времени, `dep_versions` сохраняется и запись
`succeeded`. Во всех вариантах `remaining=0`, `ticket=null`. Затем выполняется
процедура запуска. Только что запущенное задание работает начиная со следующего
такта. Пустая система также продвигает время.

### `{"op":"cancel", "id":"a"}`

Отменить само `a` и **всех транзитивных потомков** в неизменном DAG. Обходить
множество отменяемых по `id`, независимо от прежнего состояния, включая
`succeeded`, `failed` и `running`. Освободить их ресурсы; установить
`state="cancelled"`, `remaining=0`, `ticket=completed_at=null`, `dep_versions={}`.
Версия и число попыток сохраняются. Для каждого ранее не отмененного задания
добавить `cancel`. Уже отмененное задание ничего не меняет и не создает запись.
Повторная отмена идемпотентна. Затем выполнить процедуру запуска.

### `{"op":"revise", "id":"a", ...}`

Разрешены необязательные `duration`, `failures`, `max_retries`, `priority`,
`resources` с теми же ограничениями, что в начальных заданиях. `deps` менять
нельзя. Сначала проверить **все** поля. Любая ошибка оставляет всю систему
неизменной, кроме списка ошибок; даже уже проверенное поле не применяется.

Применить переданные параметры только к `a`. Для `a` и всех его транзитивных
потомков, по `id`: освободить ресурсы, увеличить `version` на 1, установить
`state="blocked"`, `attempts=remaining=0`, `ticket=completed_at=null`,
`dep_versions={}` и добавить `revise`. Параметры потомков сохраняются. Это
инвалидирует и прошлый результат, и выполняющуюся попытку, и отмену. Даже обновление
без параметров создает новые версии; `revise` не является идемпотентным. Затем
выполнить процедуру запуска. Завершение прерванной попытки позднее не возникает.

### `{"op":"checkpoint", "name":"x"}`

Имя — непустая строка, лишние поля запрещены. Если такого имени еще нет, сохранить
независимую глубокую копию заданий **со всеми параметрами**, времени, счетчика
билетов, владельцев ресурсов и истории. Никакого запуска и записи в историю нет.
Существующий снимок не перезаписывается; повторение идемпотентно.

### `{"op":"restore", "name":"x"}`

Имя — непустая строка, лишние поля запрещены. Восстановить глубокую копию перечисленных
выше данных из снимка. История откатывается вместе с состоянием, после чего в нее
добавляется `{"t":восстановленное_время,"kind":"restore","name":"x"}`.
Никакой дополнительной процедуры запуска нет. Сам снимок остается неизменным.
Реестр **всех** имен снимков и список ошибок не откатываются. Таким образом снимок,
созданный после восстанавливаемого, также остается доступен. Повторные восстановления
возвращают одно и то же состояние и одну запись `restore` после исходной истории.

## Ошибки и атомарность

Неверное событие добавляет `{"index":i,"code":код}` в `errors`, где i — индекс
события во входе, начиная с 0. Оно не меняет часы, задания, очередь, ресурсы, снимки
и историю, не выполняет процедуру запуска. Продолжить со следующим событием.
Порядок выбора кода:

1. Не объект или `op` не один из пяти операторов: `UNKNOWN_OP`.
2. Для `cancel`/`revise` отсутствующий, нестроковый либо неизвестный `id`:
   `UNKNOWN_JOB`, даже при других неверных полях.
3. Для известного оператора неверные/лишние поля: `BAD_EVENT`.
4. Для корректно оформленного `restore` неизвестное имя: `UNKNOWN_CHECKPOINT`.

Отсутствующие обязательные поля также неверны. Проверка `resources`: именно список,
все элементы — непустые строки, повторов нет. Некорректные входные **начальные**
задания и дополнительные верхнеуровневые поля не входят в тестируемый контракт.

## Результат

Вернуть ровно поля:

| Поле | Содержание |
|---|---|
| `time` | Текущее целое время |
| `next_ticket` | Следующий свободный номер билета |
| `jobs` | Массив по `id`; каждый объект содержит ровно `id`, `version`, `state`, `attempts`, `remaining`, `ticket`, `completed_at`, `dep_versions` |
| `queue` | `id` всех `ready` по ключу `(-priority,ticket,id)` |
| `locks` | Объект ресурс → `id` текущего владельца |
| `checkpoints` | Все сохраненные имена по строковому порядку |
| `history` | Массив записей в порядке операций, с учетом откатов |
| `errors` | Все ошибки во входном порядке, без откатов |

Записи `start`, `retry`, `failed`, `succeeded`: ровно `t`, `kind`, `id`, `version`,
`attempt`. Записи `cancel`, `revise`: ровно `t`, `kind`, `id`, `version`.
Формат `restore` указан выше. Порядок ключей JSON-объектов не оценивается; порядок
массивов оценивается. Состояния: `blocked`, `ready`, `running`, `succeeded`, `failed`,
`cancelled`. Только `ready` имеет ненулевой в смысле наличия билет (номер 0 допустим),
только `running` имеет положительный остаток, только `succeeded` имеет время
завершения. Ввод и возвращенные ранее результаты нельзя изменять последующими вызовами.

`visible.json` содержит примеры с полными ожидаемыми результатами. Открытые тесты
из корня комплекта: `python -m advanced check M02`; для своей копии проекта
добавьте `--project ПУТЬ_К_ПРОЕКТУ`.
