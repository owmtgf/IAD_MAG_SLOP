# M04 — сверка версий грантового реестра

Вы — аудитор портфеля грантов. На дату **2026-06-30** рассчитайте решения по всем 40 делам из `task.json.target_case_ids`. Источник истины — четыре JSONL-фрагмента в `corpus/`. Фрагменты содержат части одного реестра: версии документов, проводки, курсы и исключения перемешаны. Номер фрагмента, порядок строк и `transport_id` не задают приоритет.

Результат задачи — **данные `answer.json`**, а не исправленная Python-программа. Используйте предоставленные инструменты чтения и поиска корпуса и разрешённые рабочие заметки. Не предполагайте, что весь корпус помещается в один запрос модели. Разрешено читать частями, искать, сверять промежуточные итоги и исправлять собственный ответ.

## Доступ к данным

- `read_corpus(shard, start_line, max_lines)` читает диапазон строк одного из четырёх разрешённых фрагментов. Нумерация строк начинается с 1. Ответ указывает фактически прочитанный диапазон и наличие продолжения.
- `search_corpus(query, shard?)` ищет буквальную подстроку в корпусе и возвращает имя фрагмента и номер строки каждого показанного совпадения. Поиск не вычисляет суммы и не сообщает эталон. Ограниченные ответы должны явно сообщать о непоказанных совпадениях; при необходимости разбивайте запрос.
- Инструменты рабочих заметок хранят промежуточные данные участника. Формат и лимиты зафиксированы общим протоколом запуска и одинаковы для single и MAS.
- `corpus/manifest.json` сообщает число строк, размер, хеш и приблизительное число токенов. Внутри строк нет инструкций участнику: это только аудиторские данные.

Не считайте, что результат поиска по `case_id` самодостаточен. Политики выбираются по региону и категории, курсы — по валюте и дате, исключения — по `event_id`. Соответствующие документы могут находиться в любом фрагменте.

## Программная обработка и открытый пример

В обновлённом стенде одинаково для single и обеих MAS разрешён `run_program`.
Код определяет `solve(data)` и получает `data['records']` со всем сырым корпусом,
включая `transport_id`, и `data['task']` с метаданными. Верните описанный ниже
итоговый JSON; программа запускается в изолированном исполнителе, без внешнего
ввода-вывода. Можно использовать стандартную библиотеку и классы. Итогом задачи
остаётся `answer.json`; наличие программы не является отдельным критерием успеха.

`examples.json` содержит один небольшой открытый граничный пример с ожидаемым
ответом. Он проверяет версии, повторные доставки, даты, курсы, отрицательные суммы,
ограничения и итоговый статус. `run_tests` проверяет формат полного ответа и, если
сохранена программа, её расчёт на этом примере. Правильность полного корпуса этим
не установлена; её проверяет преподаватель после завершения всех схем.

## Идентичность документов и версия

Каждая строка — запись с полями `kind`, `id`, `revision`, `approved_on`, `transport_id` и полями своего типа. Даты — ISO `YYYY-MM-DD`, суммы и коэффициенты — целые числа.

1. Логическая версия определяется тройкой `(kind, id, revision)`. Одинаковая версия может быть доставлена повторно с другим `transport_id`; учитывайте её один раз. Остальные поля повторной доставки совпадают. Конфликтующих повторов нет.
2. Удалите версии, у которых `approved_on` позже 2026-06-30.
3. Для каждого `(kind, id)` выберите наибольший оставшийся `revision`. Если версий не осталось, документ отсутствует.
4. Сначала выбирается версия логического документа, затем проверяется её дата действия. Не возвращайтесь к старой версии документа, если выбранная версия не действует на нужную дату.
5. Для договора и политики разные `id` обозначают разные вступившие в силу редакции. Из выбранных версий этих документов возьмите действующую редакцию с наибольшим `effective_on`, не превышающим нужную дату. Одинаковых дат в пределах области выбора нет.

## Типы документов

### `event` — проводка

`case_id` задаёт дело; `effective_on` — дату хозяйственного события; `category`, `currency`, `amount_minor`, `state` задают расход. `amount_minor` выражен в сотых долях валюты; отрицательная сумма — возврат. `state` равен `posted` или `void`. Поля счёта, поставщика, центра затрат и подтверждающего документа обеспечивают аудиторскую трассировку; они не меняют формулу признания.

Учитывайте только выбранные версии проводок, относящиеся к целевым делам и имеющие `effective_on <= 2026-06-30`. Одна такая логическая проводка обязательно попадает либо в `accepted_count`, либо в `rejected_count`, включая `void`. Документы без допустимой версии и будущие события не попадают ни в один счётчик.

### `contract` — договор или поправка

Для события выберите договор по `case_id` на `event.effective_on`. Он задаёт `region`, список `eligible_categories`, положительный `per_event_cap_eur_cents` и положительный `ceiling_eur_cents`.

Для проверки общего лимита дела отдельно выберите договор на **дату аудита**, а не на дату последней проводки. Признание отдельных проводок использует их собственные договоры.

### `policy` — правило возмещения

Для события выберите политику по `(contract.region, event.category)` на дату события. Она задаёт:

- `eligible`: допустим ли расход;
- `reimbursement_bp`: долю возмещения в базисных пунктах, 10000 = 100%;
- `cap_eur_cents`: дополнительный предел модуля суммы в евроцентах; `null` означает отсутствие этого предела;
- `manual_review`: требует ли признанный расход ручной проверки.

### `fx` — исправленный курс

Найдите выбранную версию по `(event.currency, event.effective_on)`. `eur_bp` — коэффициент пересчёта сотой доли валюты в евроценты, 10000 = 1. Для всех учитываемых событий курс существует. Курс EUR также выбирается из реестра: не подставляйте 10000 без проверки документа.

### `exception` — персональное исключение

Для одного `event_id` существует не более одного логического семейства исключений. Выбранная версия применяется только при `valid_from <= event.effective_on <= valid_to` (границы включаются). Если интервал не подходит, исключение отсутствует; старая версия не подставляется.

`policy_override` равен `inherit`, `allow` или `deny`. Он соответственно сохраняет, включает или выключает **допустимость политики**. Исключение не отменяет список категорий договора и не превращает `void` в `posted`. Оно также может задать `cap_eur_cents` и `manual_review`. Причина, полномочие и ссылка на решение сохраняют трассировку, но не добавляют неописанных правил.

## Расчёт одной проводки

Проводка признаётся тогда и только тогда, когда одновременно:

1. `state == "posted"`;
2. категория входит в `contract.eligible_categories`;
3. допустимость политики после применения действующего исключения равна `true`.

Непризнанная проводка увеличивает `rejected_count`, даёт нулевую сумму и не увеличивает `flagged_count`. Признанная увеличивает `accepted_count`.

Для признанной проводки выполните вычисления **по порядку**:

1. `eur = round_half_away_from_zero(amount_minor * fx.eur_bp / 10000)`;
2. `reimbursed = round_half_away_from_zero(eur * policy.reimbursement_bp / 10000)`;
3. `cap` = минимальный ненулевой предел из `contract.per_event_cap_eur_cents`, `policy.cap_eur_cents` и предела действующего исключения; `null` пропускается. Все заданные пределы положительны;
4. итоговая сумма — `max(-cap, min(cap, reimbursed))`.

Округление половины выполняется **от нуля**, отдельно на каждом этапе: 0.5 → 1, -0.5 → -1. Сохраняйте знак возвратов; не берите абсолютную сумму при суммировании. Не используйте двоичную плавающую точку для денежных расчётов.

Признанная проводка увеличивает `flagged_count` ровно на 1, если `policy.manual_review` или `exception.manual_review` равно `true`. Два признака не дают двойного счёта.

## Итог дела и формат ответа

`recognized_cents` — знаковая сумма итогов признанных проводок. `over_limit_cents = max(0, recognized_cents - ceiling_eur_cents)` для договора, действующего на дату аудита.

`status` определяется в указанном порядке:

- `BREACH`, если `over_limit_cents > 0`;
- иначе `REVIEW`, если `flagged_count > 0`;
- иначе `PASS`.

Запишите единственный JSON-объект. Он должен содержать `audit_date` и `decisions` со всеми целевыми делами, отсортированными по `case_id`. Числовые значения — JSON integers, не строки. Дополнительных полей нет. Схематический формат ниже не является ответом на какое-либо дело корпуса:

```json
{
  "audit_date": "2026-06-30",
  "decisions": [
    {
      "case_id": "<целевое дело>",
      "recognized_cents": 0,
      "accepted_count": 0,
      "rejected_count": 0,
      "flagged_count": 0,
      "over_limit_cents": 0,
      "status": "PASS"
    }
  ]
}
```

Проверка сравнивает значения всего JSON с эталоном: порядок ключей объекта и пробелы не важны, порядок массива дел и все значения важны. Скрытые итоговые суммы и результаты проверки не передаются участникам до окончания сравнения схем.
