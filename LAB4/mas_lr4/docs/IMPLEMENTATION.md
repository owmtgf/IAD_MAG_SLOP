# Реализация двух архитектур

## Граница вашей работы

Редактируйте `maslab/student_policies.py` и пять инструкций ролей:
`programmer.txt`, `reviewer.txt`, `coordinator.txt`, `developer.txt`, `tester.txt`.
Добавляйте собственные тесты в `tests/`. Не меняйте baseline, `base.txt`, Engine,
исполнитель, провайдер, исходные задачи и ожидаемые ответы. Ошибку стенда сообщите
преподавателю: исправление должно быть одинаковым для всей группы.

Если меняете схему хранения состояния, размещайте весь код внутри
`student_policies.py`, чтобы заморозка однозначно фиксировала реализацию.
Библиотеки агентов не нужны; прямые обращения к модели в обход Engine запрещены.

## Общий интерфейс

`fixed(engine)` и `coordinator(engine)` ничего не возвращают. Для успешного
завершения нужно вызвать `engine.finish()` и получить True.
Engine сам вызывает финальную проверку и сохраняет код, расход и статус.

| Метод | Что делает |
|---|---|
| `run_role(role, instruction, max_turns)` | Даёт роли задачу и до max_turns модельных действий; возвращает передачу результата |
| `coordinator_decision(feedback)` | Один вызов координатора; возвращает JSON, который нужно проверить |
| `current_report()` | Реальный отчёт только для текущего хеша кода; иначе None |
| `finish()` | Проверяет текущий код инструментом; True только после прохождения |

Передача результата роли содержит `message`, `finish_requested`, `code_sha256`,
`verified_report`. `message` - слова модели. `verified_report` - данные стенда.
Сохраняйте это различие. Отдельные истории ролей хранятся в `engine.histories`;
актуальный код и отчёт общие. При редактировании старый отчёт теряет силу.

Любой вызов LLM, включая координатора и ревьюера, оплачивается из одного бюджета.
`EpisodeStop` останавливает эпизод автоматически; не перехватывайте его ради продолжения.
Не меняйте `engine.tokens`, `finished`, `report`, `cases` и содержимое журналов.
Для изменения программы используйте инструменты роли, а не присваивание `engine.code`.

## 1. Фиксированный процесс

Обязательная последовательность: programmer → reviewer → programmer → проверка.
Программист может внутри своего этапа читать, исправлять и запускать тесты несколько
раз. Ревьюер читает и проверяет, но не редактирует. Последний этап получает замечания
ревьюера и фактическое состояние проверки. Возврат finish от первой роли означает
конец её этапа, а не пропуск оставшихся этапов.

Задайте и объясните конечное число действий на каждом этапе. Сумма допустимых
вызовов не должна обходить общий `max_model_calls=48`. Фиксированный порядок
сохраняется даже тогда, когда первая версия уже проходит тесты. Это цена этой схемы.

## 2. Координатор

Обязательны отдельные контексты coordinator, developer и tester.
Координатор выбирает следующую роль по обратной связи и может повторно вызвать её.
Постоянный порядок developer→tester без реального решения координатора не считается
этой архитектурой. Координатор не редактирует код сам.

Допустимы ровно такие формы решения:

```json
{"action":"delegate","role":"developer","instruction":"исправь обработку границы"}
```

```json
{"action":"delegate","role":"tester","instruction":"проверь код и сформулируй замечания"}
```

```json
{"action":"finish"}
```

Проверьте поля, типы, допустимую роль и длину инструкции (не более 6000 символов).
На неверное решение верните понятную обратную связь; уже потраченные токены не
возвращаются. Ограничьте число маршрутизаций. Завершение допустимо только после
True от `engine.finish()`. При неуспехе верните координатору фактический отчёт.

## Инструменты модели

| Действие | Доступ и результат |
|---|---|
| `read_code` | Текущий полный код и SHA-256 |
| `replace_code` + `code` | Только single/programmer/developer; заменяет весь модуль |
| `run_tests` | Реальные открытые проверки с ожиданием, результатом, типом ошибки и хешем |
| `yield` + `message` | Завершает этап роли, передаёт краткий текст |
| `finish` | Просьба завершить; решение принимает управляющий код через реальную проверку |

Тестер может анализировать дополнительные крайние случаи словами. Добавлять или
менять оцениваемые тесты он не может. Во всех схемах общий исполнитель и одинаковые
открытые данные; права отдельных ролей определяются их обязанностями.

## Что обязательно проверить самостоятельно

Добавьте минимум четыре содержательных offline-сценария на вашу маршрутизацию:

1. Первая версия уже правильная: fixed всё равно проходит три этапа.
2. Ревьюер нашёл ошибку: его замечание реально получает заключительный программист.
3. Координатор выбрал неизвестную роль или неправильный JSON: обработка не ломается.
4. Модель просит finish на неправильном/изменённом после проверки коде: успех не засчитывается.

Используйте `ScriptedProvider` из `tests/test_harness.py` и маленькую свою функцию.
Не выдавайте такие сценарии за ответы настоящей LLM. Они проверяют логику стенда.

## Сохраняемые данные

В каждом эпизоде: `trace.jsonl`, `main.py`, `result.json`.
Трасса содержит входы/выходы модели, роль, фактический usage, результаты инструментов,
код правок, хеши и время. API-ключ не записывается.
`result.json` содержит `tokens_by_role`, общий расход, статус, превышение бюджета,
количество вызовов и финальный отчёт. Используйте это для объяснения различий.
