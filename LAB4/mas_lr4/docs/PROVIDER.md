# Подключение реальной модели

Стенд содержит маленький HTTP-адаптер. Ему нужен endpoint, реализующий указанный ниже
контракт Chat Completions. Совместимость с произвольным провайдером не гарантируется.
Преподаватель до выдачи работы выбирает и проверяет один доступный endpoint/модель.
Для новых задач сохранены отдельные модельные калибровки. Они не являются
пилотом этого HTTP-адаптера; выбранный группой endpoint нужно проверить до выдачи.

## Настройка

`MAS_LLM_BASE_URL` - базовый URL API, обычно оканчивается на `/v1`.
Адаптер добавляет `/chat/completions`. `MAS_LLM_API_KEY` - ключ (для локального endpoint
может отсутствовать). В `config.json` замените `SET_MODEL` на точный идентификатор.
Ключ не записывайте в JSON, инструкции или код. Не присылайте его преподавателю.

Bash: задайте URL своей системы, затем введите ключ скрытым вводом.

```bash
export MAS_LLM_BASE_URL='https://YOUR_PROVIDER/v1'
read -rs -p 'API key: ' MAS_LLM_API_KEY
export MAS_LLM_API_KEY
```

PowerShell: `$env:MAS_LLM_BASE_URL='https://YOUR_PROVIDER/v1'`; ключ задайте через
механизм секретов вашей среды. URL выше - образец, его нужно заменить, не запускать.

## Точный контракт адаптера

HTTPS POST, заголовки Content-Type: application/json, Authorization: Bearer KEY
(если ключ задан). Для локального localhost/127.0.0.1 допускается HTTP.
Тело: `model`, `messages` (роли system/user/assistant), `temperature`, `max_tokens`.
При `send_seed=true` добавляется `seed`. Streaming, нативные tool calls и JSON mode
не нужны: действия передаются текстовым JSON в `choices[0].message.content`.

Ответ должен содержать:

```json
{
  "choices": [{"message": {"content": "{\"action\":\"run_tests\"}"}}],
  "usage": {"prompt_tokens": 800, "completion_tokens": 20, "total_tokens": 820},
  "model": "actual-model-version",
  "id": "provider-request-id"
}
```

Числа здесь иллюстрируют формат, а не результаты эксперимента.
Все три usage-поля обязательны, целые и согласованные. Если провайдер использует
другой endpoint, название ограничения генерации или поля usage, преподаватель
адаптирует `provider.py` один раз ДЛЯ ВСЕЙ группы и повторяет пилот до заморозки.
Нельзя просто удалить учёт расхода или записывать выдуманные значения.

Для модели со скрытыми reasoning-токенами проверьте, что `completion_tokens`
включает все оплачиваемые выходные токены; если нет, адаптер требуется исправить
по фактическому контракту провайдера. В итогах записывайте модель, endpoint, дату,
температуру и фактически возвращённый `model`. Изменение версии во время запуска
отмечайте как ограничение воспроизводимости.

## Что показывает пилот

Пилот на D01,D06,D11,D16,D21 отвечает на три вопроса: проходит ли формат запросов;
корректно ли возвращается usage; не слишком ли лёгкие задачи/малый бюджет для
выбранной модели. После реализации двух схем - 5 × 3 × 2 бюджета × 1 повтор =
30 эпизодов. Это калибровка на dev, не итоговые выводы по 50 test.

Проверьте, что есть рабочие ответы и содержательные отличия трасс, а не только
ошибки транспорта/формата. Если все три схемы дают одинаковые 100% с первого шага,
исследуйте стоимость и лишние действия; не добавляйте искусственные запреты только
одиночному агенту. Если почти все ответы обрываются, измените лимит ответа/бюджеты
одинаково для всех до test и отразите это в протоколе.
